# Repository Guidelines

## Project Structure & Module Organization

- `src/main.ts` contains the Obsidian plugin lifecycle, commands, context-menu integration, editor decorations, and Reading view postprocessor.
- `src/core.ts` contains pure parsing, fence detection, selection, and `hl:` range logic. Keep this module independent from Obsidian APIs.
- `src/settings.ts` defines persisted visual settings and the settings tab.
- `tests/*.test.ts` contains Vitest unit and integration-style tests for core behavior and settings normalization.
- `styles.css` provides the autonomous editor and Reading view rendering. `manifest.json` and `versions.json` contain Obsidian release metadata.
- `main.js` is generated by the build. Do not edit it directly or commit dependencies, vault data, or machine-specific files.

## Build, Test, and Development Commands

Use Node.js 18 or later and pnpm.

```bash
pnpm install       # install exact dependencies from pnpm-lock.yaml
pnpm run dev       # rebuild main.js while files change
pnpm run build     # type-check and create the production bundle
pnpm run lint      # run ESLint and Obsidian-specific rules
pnpm test          # run the complete Vitest suite once
```

Before submitting a change, run build, lint, and tests. For visual changes, also load the plugin in Obsidian and inspect both Live Preview and Reading view.

## Coding Style & Naming Conventions

Follow `.editorconfig`: UTF-8, LF endings, a final newline, and tabs with width 2. Use TypeScript strict typing, `camelCase` for functions and variables, `PascalCase` for classes and types, and descriptive command or CSS class names. Prefer type-only imports where applicable. Keep document transformations pure in `core.ts`; Obsidian-specific mutations belong in `main.ts`. Preserve code-block contents and apply editor changes as one transaction.

## Testing Guidelines

Use Vitest with files named `tests/<area>.test.ts`. Add focused cases for valid behavior and rejection paths. Fence parsing tests should cover backticks and tildes, metadata whitespace, quoted text, reversed or partial selections, LF/CRLF, malformed ranges, and unchanged-document guarantees. Rendering or settings changes require manual verification because DOM layout is not fully covered by unit tests.

## Commit & Pull Request Guidelines

History follows Conventional Commits, for example `fix: preserve Reading view highlights` and `feat: add configurable colors`. Keep commits scoped and imperative. Pull requests should explain the user-visible behavior, list validation commands, link relevant issues, and include screenshots for visual changes. Update `manifest.json`, `versions.json`, and `package.json` together when releasing a new version; release assets are `main.js`, `manifest.json`, and `styles.css`.
